# FreshLink 前端与联调开发任务书

**发给：前端开发同学 B**  
**项目：面向连锁餐饮的生鲜食材仓储与配送管理系统**

## 项目在做什么

FreshLink 是在现有 WMS 上增量改造的课设系统。目标是让一个总部配送中心服务多个连锁门店，完成食材与供应商/门店资料维护、按批入库和效期管理、门店申领、仓库审核与分配、拣货、内部配送、门店签收、异常处置、批次追溯、业务看板和只读 AI 库存查询。

系统角色有总部管理员、仓管/配送调度、门店用户。门店用户只能操作绑定门店的数据；一期每个门店用户绑定一个门店。食材采用固定包装整数数量，例如“鸡胸肉 1kg/袋”，不做散装称重、拆包或单位换算。项目沿用现有 Vue 管理端和 Java 后端，不增加第二套库存账，不做地图、GPS、司机 App 或路线优化。

P0、P1 均已独立验收通过。P1 报告见 `work/fresh-acceptance/P1/attempt-02/codex-review.md`。P2 尚未开始；拿到项目负责人提供的 GitHub 已验收基线后再开工。

## GitHub 起步条件

当前 FreshLink 根目录不是 Git 仓库；`apps/backend` 与 `apps/web` 是两个独立仓库，现有 `origin` 分别指向 Gitee。两个仓库都含有效的未提交和未跟踪成果，因此 HEAD 不等于完整可工作的基线。本次未提供且尚未核实可用的 GitHub 地址与 `p1-accepted` 基线 tag/SHA。当前两个仓库的 `origin` 配置指向 Gitee，团队开工前需由负责人确认 GitHub 地址和 remote。

建议项目负责人在 P1 通过后建立新的**私有 GitHub 单仓 FreshLink 工作副本**，纳入届时冻结的完整有效源码、`specs/`、`scripts/`、项目说明、脱敏配置模板，以及筛选过的迁移和验收资料，继续保留 `apps/backend`、`apps/web` 目录。当前未执行 GitHub 迁移或推送。原本机目录与两个 `.git` 历史留作只读来源；不得在原目录删 `.git`、重置或清理。负责人发出 GitHub URL 和 `p1-accepted` 基线 tag/SHA 后，所有人从此基线开分支。不能把原 Gitee 克隆当成完整基线，也不能 push 到原来的 `origin`。

不要提交 `runtime/config` 中的真实凭据、`runtime/backups`、数据库备份、`runtime/cache`、`node_modules`、Maven `target`、前端 `dist`、本机运行数据或含密钥/个人信息的日志和截图。源码 YAML 与历史配置也可能包含凭据；负责人整理可分享基线时须检查 `application-dev.yml` 等文件并改成占位模板。完整本机快照仅在本机留存，不直接上传。逐项暂存本批文件并检查 `git diff --cached`；命令示例中的路径占位符须换成实际路径。不要用 `git add .` 盲目全选。commit 是本地记录，push 才上传 GitHub。只 push 指定 GitHub remote 的本人分支，不自行合并主分支、不 force push。

## 合同和提交节奏

每阶段 A 先提供 API/数据合同，包含路径、请求和响应字段、角色数据范围、状态、数量/日期规则、业务错误、重试幂等、迁移顺序。你确认可以接入后再开始页面；若字段或行为不够清楚，先提出具体问题，由 A 更新合同并让负责人知情。不能从客户端传入可信 `storeId`、库存数、批次号事实或状态去“补足”后端行为。

同一阶段你可以和 A 并行开发，但页面只针对冻结合同实现。双方 PR 分别通过代码审查后，负责人再对组合版本按 `validation.md` 做阶段验收。阶段只有明确通过后才进入下一 P。每批 PR 是一次可独立复查的交付；提交后暂停当前批次并等待反馈，不要先做完整个阶段才提交。你必须自测并准备真实浏览器/接口联调证据；负责人的验收不替代开发测试。

分支示例：`feat/p2-batch-ui`、`feat/p3-requisition-ui`。从负责人提供的 GitHub 基线创建分支；前一批合入主分支后，新批次从最新主分支开分支。若依赖 PR 尚未合并，注明依赖 PR，不从过时的 P1 基线重复分叉。操作示例（仓库地址、remote 和目标分支由负责人提供）：

```bash
git clone <负责人提供的GitHub仓库地址> FreshLink
cd FreshLink
git switch --detach <负责人提供的p1-accepted-tag或SHA>
git switch -c feat/p2-batch-ui
git add -- <本批实际修改的文件路径>
git diff --cached --stat
git commit -m "feat(p2): add batch inventory pages"
git push <负责人确认的GitHub-remote> feat/p2-batch-ui
# 在 GitHub 创建 PR；目标分支使用负责人指定的受保护主分支
```

在指定 GitHub remote 的本人分支开 PR，目标主分支由负责人确认；不得自行合并。Draft PR 可同步进度；本批适用页面、构建/测试和证据完成后才标 Ready。

每个 PR 描述写清：关联验收号、本批前端 SHA 和后端候选 SHA、所用 API 合同版本、页面/路由/组件变更、适用构建和测试命令/退出码/实际断言数、浏览器截图与操作步骤、失败请求响应（脱敏）、尚未实现内容和回退方式。早期批次只验证已经实现的行为及可使用的接口，不等待阶段后续批次代码；阶段最后一批再完成整阶段回归。页面加载成功、HTTP 200、Vite 转换通过都不等于业务操作通过。

## 页面必须遵守的业务规则

- 库存 `stockQuantity = availableQuantity + allocatedQuantity`；available 是账面未分配。可配送数还要过滤效期、质量、来源完整性和可拣储位，页面不能把旧 available 字段直接标成可配送。
- 食材按固定规格整数计数；输入只接受正整数。签收 A/R/M 是非负整数，单项 0 合法，每个批次必须满足 `A+R+M=F`。越界/溢出由后端拒绝，前端显示清楚错误，不悄悄四舍五入。
- 批次 ID 和到期日由后端事实返回并贯穿页面；用户不能改批次来源或日期来绕过效期。按 FEFO 结果展示批次明细。
- 只有确认发车扣中央仓库存；派单、签收不再扣。发生拒收/短缺时页面清楚提示不自动回仓。
- 禁用门店后，既有单据仍要能查询和签收；“读取历史单/识别本店”与“允许创建新业务”是两种不同校验。遇到旧单被禁用状态挡住时报告 A 处理，不用前端规避授权。
- P2/P3 新增批次/申领引用后要由 A 更新后端 `FreshReferenceGuard` 删除保护；前端删除按钮状态不能替代后端保护。
- 全部越权控制由服务端完成。前端隐藏按钮只是呈现，不能当权限实现；检查详情、分页、导出、统计、批量操作以及 AI。
- 全量 `vue-tsc` 仍有已记录的存量诊断，检查器非零退出。新代码不得增加诊断；报告应附基线比较结果，不得称全量类型检查通过。新增页面自身错误和影响本阶段构建/功能的类型错误仍需修复。
