# FreshLink D2 入库与效期接口合同

基线为 v2.1 与远端 main 的 D1 合并版本 `f2a5743`。复用原入库、收货任务、上架任务和库存页面接口。总部、仓管可用，门店权限沿用 P1。JEECG 响应保持 `Result` 格式，前端以 `success` 和 `message` 判断结果。

| 动作 | 接口及请求 | 状态与数据 |
| --- | --- | --- |
| 保存计划 | `POST /inorder/wmsStockInOrders/add` 或 `PUT /inorder/wmsStockInOrders/edit`，在现有表单加 `supplierId`，每条 `wmsStockInOrderItemsList` 明细传 `productId`、`expectedQuantity`、`batchNumber`、`productionDate`、`expiryDate` | 一条明细指定一个供应商批次。原提交审核、审核和明细查询接口保留。 |
| 创建收货任务 | `POST /inorder/receiveTasks/add`，沿用 `orderIds`、`operator` | 单据 `APPROVED` → `RECEIVING`，生成各明细任务。 |
| 收货 | `POST /inorder/receiveTasks/addRecords`，JSON `{id, execQuantity, targetLocationCode, requestKey}` | `id` 是任务 ID。目标为该仓启用的收货暂存位（如 R1）。批次和日期由入库明细读取。全单收完成为 `RECEIVED`，生成上架任务。 |
| 上架 | `POST /inorder/putawayTasks/addRecords`，JSON `{id, execQuantity, targetLocationCode, requestKey}` | 来源储位由任务确定。目标为启用且温区匹配的良品正式储位（存储位/拣选位）。状态为 `PUTAWAYING` 或 `PUTAWAYED`。 |
| 查询库存 | `GET /inventory/wmsInventory/list`，沿用分页 | 返回商品、来源供应商、批号、生产及到期日、入库引用、位置和数量。 |

日期用 `YYYY-MM-DD`，按 Asia/Shanghai 当日验证。收货时生产日不得晚于当日，到期日晚于生产日和当日。正向数量为 JSON 整数 1～2147483647，整张入库单计划合计不得超过 2147483647。收货和上架可分次，同一次请求重试须复用同一个 `requestKey`（建议 UUID），新的分批动作使用新键。相同任务键和参数重试返回成功，换参数复用请求键会返回业务错误。服务端从任务和单据读取商品、批次、日期及来源位置。

库存效期状态为 `EXPIRED`（剩余天数≤0）、`NEAR_EXPIRY`（大于0且不超过阈值）、`NORMAL` 和 `PENDING_VERIFICATION`（历史缺来源）。库存账面未分配量是 `availableQuantity`，符合出库资格的数量是 `eligibleQuantity`。D3 使用库存行 ID 与内部 `stockBatchKey` 识别库存批次，界面展示供应商 `batchNumber`。

查询库存详情保留 `GET /inventory/wmsInventory/queryById?id=...`。列表和详情均提供 `supplierId`、`supplierName`、`productSpec`、`unit`、`inboundOrderId`、`inboundOrderItemId`、`inboundOrderNumber`、`stockBatchKey`、`batchNumber`、`productionDate`、`expiryDate`、`remainingDays`、`expiryStatus`、`eligibleQuantity`。分开的入库明细保留各自来源。库存余额和流水使用同一个内部批次键 `FL:<入库明细ID>`。

## 数据库升级与回退

已有 D1 数据库在确认库名并备份后执行 `apps/backend/db/fresh/D2_00_inbound_lots.sql`，再启动 D2 后端。新库用团队初始化脚本。迁移扩充来源字段、内部批次键长度、入库明细唯一键和请求去重索引，旧余额与旧占用保留。收货和上架只能由原业务动作修改库存。

回退应用前按是否已经产生 D2 单据与流水选择路径。尚无 D2 数据时可使用迁移前的应用和备份恢复。已有 D2 数据时保留对应版本和数据，依据独立备份恢复点制定回退方案，避免丢失多批明细或将内部批次键截断。

## D3 出库路径核实

现有 `WmsOutOrdersServiceImpl.allocateStock` 返回分配失败，`WmsWaveMasterServiceImpl.createWave` 留有创建逻辑 TODO。旧 `WmsWaybillServiceImpl.send` 依赖波次和拣货记录，并在发货时调用旧扣减，扣的是在库与已分配量。D3 人工选批可直接按库存行和 `stockBatchKey` 读取和锁定原库存，确认时校验来源、效期、正式位置和未分配量，再于同一事务写负数流水、扣在库及未分配量和生成配送单。D2 已保护新批次免受旧分配及拣货动作修改。

## 复测

1. 建立独立的 `freshlink_d2_*` 测试库，初始化到 D2。只在该测试库中以 MySQL 客户端执行 `scripts/team/fixtures/D2-isolated-negative-data.sql` 一次，准备到期当天和缺来源历史两种边界。B1/B2 及其他正向库存由真实 API 收货、上架。
2. 使用合法登录取得该隔离环境仓管的访问令牌和用户 ID。在当前终端设置 `FRESHLINK_ACCESS_TOKEN`、`FRESHLINK_OPERATOR_ID`、`FRESHLINK_API_ROOT`（默认 `http://127.0.0.1:18082/jeecg-boot`）、`FRESHLINK_EVIDENCE_DIR`（仓库 `work/` 下的空目录），执行 `python scripts/Invoke-FreshD2ApiProbe.py`。退出码 0 表示已记录的 HTTP 断言通过。
3. 后端测试使用 `mvn -Pp0-tests -pl jeecg-module-system/jeecg-system-start -am package`。团队 Maven 环境沿用 `scripts/team/Test-Team.ps1` 中的 settings 文件和项目内缓存参数。最终业务验收使用当前组合版本。
