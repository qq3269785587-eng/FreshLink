# FreshLink 后端与数据库任务书

版本 v2.1 · 2026-11-18 · 两天课堂演示版

项目题目：面向连锁餐饮的生鲜食材仓储与配送管理系统。

两天内以课堂演示为目标，在原 WMS 和已验收的 P0、P1 上先补齐演示范围内的基础功能，再跑通生鲜入库、库存效期、人工选批出库与简单配送。D1、D2、D3、D4 均待实施；P0、P1 保持已验收状态。本任务书替代旧 P2～P7 安排。

## 工作范围与协作

阶段分支建议：D1 使用 `feat/a-d1-basics`（A）/`feat/b-d1-basics`（B）；D2 使用 `feat/a-d2-inbound` / `feat/b-d2-inbound`；D3 使用 `feat/a-d3-delivery` / `feat/b-d3-delivery`；D4 使用 `feat/a-d4-demo` / `feat/b-d4-demo`。每个阶段完成本人部分、自测并提交 PR，负责人合并后，从最新 main 开始下一阶段。


你负责 apps/backend、增量 SQL、业务权限、事务和后端测试；前端同学负责 apps/web、页面联调及演示材料。共享接口合同和根脚本先约定归属，保留对方修改。你完成每阶段后提交、推送本人分支并开 PR，负责人审查和合并；最终组合版本由负责人验收。

本次保留一个配送中心、多个门店、固定包装整数计数。总部或仓管统一操作，门店账号保留 P1 本店只读权限。

AI、门店申领审批、自动 FEFO、波次拣货、门店逐批签收、拒收短缺、退货、门店库存、IoT、地图、复杂看板和全新机器部署移出本次必做。保留旧代码，隐藏无关或不可运行入口。基础资料页面纳入必做范围，检查商品、供应商、门店、仓库、库区、储位的查询、新增、修改、必填/重复校验和状态实际生效；禁用仓库、库区或储位不得用于新的上架，历史记录仍可查，不能因此误拦已有库存的出库或已出库配送。删除主数据时按现有引用关系保护，避免破坏历史单据。

确认出库是唯一扣库存动作：同一事务按批扣账、记录流水、锁定出库事实并生成唯一待配送单。配送仅“待配送 → 配送中 → 已送达”，状态变化不再扣库。送达是仓管登记，不宣称门店签收；已出库不允许改数量或取消回库。

先提交一份简短接口合同：字段、请求响应、角色、状态映射、错误提示和数量口径。前端确认后双方并行，每天集中集成；每批完成即可提 PR，不等整个系统结束。

代码仓库：https://github.com/yukisuki7/FreshLink。代码基线为 p1-accepted；它不含本次新规格。开工前先等负责人将规格文档 PR 合入 main，并确认 main 已含 specs v2.1，再从最新 main 创建本人阶段分支，不检出旧标签覆盖新文档。仓库无写权限时，fork 后从个人 fork 开分支并向上游仓库提 PR。

团队克隆目录即工作根，使用根 README、docs/团队本机开发指南.md 和 scripts/team/ 配置自己的数据库及账号，不照搬原机固定库名、密码或端口。下载和缓存放项目内，不放 C 盘。首次写入前核验实际库、后端构建和前端代理，不能用原业务库做测试。

## 两天要完成的实现

### D1 · 基础模块补全（第一天上午）

- 仓库筛选：名称、属性、状态可组合查询，清空条件后恢复完整列表。
- 库区编码：新增和修改均由后端校验唯一性，修改时排除当前记录；重复编码被拒绝且数据不变，不能只依赖前端提示。
- 库区状态：提供禁用操作并持久化；禁用库区不可用于新上架，历史数据仍可查询。
- 储位筛选：储位编码、所属仓库、所属库区可组合查询。
- 储位状态：支持启用和禁用；禁用储位不可用于新上架，历史库存可查询。
- 核查商品、供应商、门店、仓库、库区、储位常用查询和新增/修改、必填与重复校验、状态效果；按外键/历史引用约束处理删除。只修演示所需缺口，不重写通用 CRUD。
- 与 B 共同冻结基础主数据接口和状态语义；提交必要 SQL/菜单/权限迁移，验证升级与重跑。



两天按 D1→D2→D3→D4 推进：第一天上午 D1 基础模块，下午 D2 入库效期并核实简化出库路径；第二天上午 D3 出库配送，下午 D4 最终联调、修复和演示彩排。原 allocateStock 是失败占位，createWave 有 TODO；不要继续补复杂波次。

- D2 批次来源：复用原商品、入库、库存表，保存供应商、食材、批号、生产日期、到期日期及入库引用；同名批号按供应商和食材区分，历史缺来源库存标为待核验，不编造来源。
- D2 收货上架：真实收货增加一次，上架同批转移且全仓不增量；重复操作和超计划收货受阻，正式储位温区匹配。扩展 P1 主数据引用保护，已有批次日期不随商品资料修改。
- D2 效期查询：按业务日期实时计算正常、临期、过期，返回批次、来源、位置和数量。到期当天不可出库，不依赖定时任务。新数据必须通过真实入库产生。
- D3 人工选批：仓管指定启用门店、批次及数量，草稿不占库存。确认时重验日期、来源、储位、食材门店启用和未分配库存；同批多行汇总检查，任一行不足整单失败。
- D3 确认出库：沿原库存服务维护一本账；扣在库及未分配相同数量，旧占用不动。条件更新或必要行锁防负数，单据终态和唯一约束防重复；库存、流水、出库和配送创建整体回滚。
- D3 配送：出库与配送一对一，保存门店地址快照和逐批明细。待配送填写配送员及联系方式后可开始配送，配送中可确认送达；记录操作人时间，禁止跳级和倒退。禁用门店不能阻断已出库配送完成。

旧通用 edit、导入和发货不得绕过新规则或二次扣库。新流程若复用旧发货代码，先修复实际使用路径的空批次问题；不另建余额表，也不通过手工改数据库余额制造完成。

SQL 用各阶段独立的新文件名放 db/fresh，包含必要菜单、字典、授权和索引；保留 P1 迁移，验证升级和安全重跑。第二天下午停止增加功能，留给演示组合版本修复和彩排。

## 验证与交付

### D1 基础模块用例（A 后端）

- D1-01 仓库按名称、属性、状态组合筛选，边界条件和清空条件正确。
- D1-02 库区新增重复编码拒绝；修改保留自身编码通过、改成其他记录编码拒绝。
- D1-03 库区禁用状态持久化。
- D1-04 储位按编码、仓库、库区组合查询。
- D1-05 储位启用/禁用状态持久化。
- D1-06 商品、供应商、门店、仓库、库区、储位新增修改、必填/重复校验及引用删除保护符合现有规则。
- D1-07 禁用仓库、库区、储位阻止新上架；历史库存仍按有效期、来源、未占用等原规则判断出库资格，不因行政禁用本身冻结库存；已出库配送可继续完成。



业务规则以 specs/生鲜课设改造/mission.md、state-contract.md 为准，具体用例以 validation.md 为准。正向动作数量为 1..2147483647 整数，拒绝空、0、负数、小数及溢出；余额可0，出库流水可负，中间求和使用足够宽类型。

- D2-01～05：真实入库上架、重复/超量/错温区、非法日期数量、临期边界、批次区分和引用保护。
- D3-01～08：正常出库、库存不足整单不扣、过期和历史库存阻断、同单重复及同时提交只扣一次、真实库失败回滚、配送状态与不重复扣库、权限旧入口回归、地址快照及禁用门店旧单可完成。
- 演示对账：B1入10袋、B2入20袋，上架总量仍30；选B1出库6后总量24，B1剩4；配送中、已送达后均为24。过期和库存不足用独立数据演示失败且余额不变。
- D4：最终组合版本构建、必要测试、本机重启和浏览器完整流程。默认 Maven package 可能跳过测试，要记录实际执行数；历史类型错误不冒称全量通过。

每阶段完成本人负责部分并完成对应自测后，立即提交、推送分支并开 PR，等待负责人审查合并 main；不自行合并。PR 写明阶段/任务编号、配套前后端分支与 PR 依赖、实际命令和结果、迁移步骤/风险、关键业务断言及未验证项。后一阶段从最新 main 新开分支；若依赖 PR 尚未合并，只基于合同推进可独立部分，不把前置依赖冒充已集成。每批只跑影响面检查，最终 D4 对组合版本验收。测试证据用新 work/fresh-acceptance/Dn/attempt-XX/，或约定的新 work 目录，不覆盖 P0/P1。

交付后端代码、增量 SQL、接口合同、可重复测试命令、简明结果及回退说明。出库一旦遇阻断立即告知前端和负责人；不要用模拟成功替代真实扣账。开发自测标“待验收”，由负责人确认通过。
