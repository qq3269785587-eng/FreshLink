**发给：后端开发同学 A**  
**项目：面向连锁餐饮的生鲜食材仓储与配送管理系统**

## 项目在做什么

FreshLink 是在现有 WMS 上增量改造的课设系统。目标是让一个总部配送中心服务多个连锁门店，完成食材与供应商/门店资料维护、按批入库和效期管理、门店申领、仓库审核与分配、拣货、内部配送、门店签收、异常处置、批次追溯、业务看板和只读 AI 库存查询。

系统角色有总部管理员、仓管/配送调度、门店用户。门店用户只能操作绑定门店的数据；一期每个门店用户绑定一个门店。食材采用固定包装整数数量，例如“鸡胸肉 1kg/袋”，不做散装称重、拆包或单位换算。系统不增加第二套库存账，也不做地图、GPS、路线优化、司机 App 或自动补货。

P0、P1 均已独立验收通过。P1 报告见 `work/fresh-acceptance/P1/attempt-02/codex-review.md`。P2 尚未开始；拿到项目负责人提供的 GitHub 已验收基线后再开工。

## 阶段协作和每批提交约定

每个阶段开始后，你先发一份版本化 API/数据合同，至少写明：接口路径和字段、角色与数据范围、状态映射、数量/日期校验、错误码或业务错误语义、事务边界、幂等规则、迁移顺序和回滚办法。B 确认合同可以联调后，再按同一阶段并行开发。接口变动先更新合同，并通知 B；不能让页面猜字段或从客户端接收可信的门店身份、库存状态、批次日期。

每个 PR 都可先做技术审查，但阶段不能只靠一个 PR 通过：后端和前端 PR 都合并到候选组合后，负责人按 `specs/生鲜课设改造/validation.md` 验收该阶段；只有阶段结论通过，才开始下一阶段。开发者必须先完成自己的单元/服务/API/真实 MySQL 测试和前后回归。项目负责人的独立验收不代替开发者测试。

分支示例：`feat/p2-batch-backend`、`feat/p3-allocation-backend`。从负责人给定的 GitHub 基线开始；已有批次合入主分支后，下一批从最新主分支开新分支。若前一依赖 PR 尚未合并，注明依赖 PR，不要反复从过时的 P1 基线创建平行分支。实际操作示例（把地址、remote、目标分支替换为负责人提供的值）：

```bash
git clone <负责人提供的GitHub仓库地址> FreshLink
cd FreshLink
git switch --detach <负责人提供的p1-accepted-tag或SHA>
git switch -c feat/p2-batch-backend
git add -- <本批实际修改的文件路径>
git diff --cached --stat
git commit -m "feat(p2): add batch receiving rules"
git push <负责人确认的GitHub-remote> feat/p2-batch-backend
# 在 GitHub 创建 PR；目标分支使用负责人指定的受保护主分支
```

按批次开小 PR，目标分支和 GitHub remote 由负责人确认。Draft PR 可同步进度；本批适用功能完成、相应用例已跑且证据齐、未完成项写明后才标 Ready。每批到下表“可以提交”处就停下等审查。不得自行合并 PR。

每个 PR 描述必须写：关联 `P?-??` 验收编号；基线和前/后端候选 SHA；API 合同版本；改动文件与 SQL 迁移顺序/重复执行结果；本批适用命令、退出码、实际测试数（通过/失败/跳过）；关键请求及脱敏响应、真实 MySQL 前后余额/状态查询；已知问题和回退方法。早期批次只验证该批已实现和可验证的断言，不要求等待阶段后续批次的代码；阶段最后一批再覆盖整阶段用例。发现状态语义或范围需要改变时先提问题，不自行删需求。

## 贯穿各阶段的规则

- 库存口径：在库 `stockQuantity = availableQuantity + allocatedQuantity`，各值不为负；`availableQuantity` 是账面未分配。可配送数量还要排除过期、不合格、冻结、待核验及不可拣库位。
- 批次 ID 必须贯穿收货、库存行、分配、拣货、发车、库存流水、配送明细和追溯。上架/拣货只移动位置，不产生第二次入库或改变到期日。
- 只有确认发车时扣中央仓库存；派单、签收不再扣。发车时库存、逐批流水、出库与配送状态同事务提交。
- 一切业务操作数量为正整数；签收的 A/R/M 为非负整数并逐批守恒。服务端检查上限，累计用 long，不能静默截断或溢出。
- 所有权限在后端执行，旧 CRUD、导入、详情、导出、统计、批量接口同样保护。HTTP 200 不代表业务成功，要看业务码和数据库结果。
- 全量 `vue-tsc` 仍有已记录的存量诊断，检查器非零退出。新代码不得增加诊断；报告应附基线比较结果，不得称全量类型检查通过。阻断本阶段业务功能的类型错误仍须修。
- 迁移在备份后的隔离 MySQL 库验证首次升级和安全重跑；失败测试要证明余额、流水、任务和状态均未变化。测试账号/数据用专用标识，保留脱敏前后查询证据。
