# 业务范围与实现规则

## 1. 目标与受众

面向连锁餐饮总部配送中心及其门店，实现“食材入仓—按批保管—门店申领—按效期出库—配送签收—异常追溯”。交付可在本地启动、能以真实数据库数据演示并可复验的课设系统。

利益相关者与账号角色：

| 角色 | 核心操作 | 数据范围 |
|---|---|---|
| 总部管理员 | 基础资料、用户门店绑定、仓储业务、配送异常处理、统计与 AI | 本课设所属组织内的全部数据 |
| 仓管/配送调度 | 入库上架、审核申领、分配拣货、派单、发车、签收异常处置 | 配送中心业务；无系统用户管理权限 |
| 门店用户 | 本店申领、本店配送查询、签收、查看结果 | 仅绑定门店的数据 |

一个门店可有多个用户；一期每个门店用户仅绑定一个门店。配送员作为配送单上的姓名/联系方式，不单独做司机登录端。总部账号可以兼任仓管进行演示，但验收必须有真实门店 A/B 独立账号。

单品牌单组织，不增加多租户 SaaS。保留现有框架认证与租户机制，不用“关闭权限”来实现简单化。货主维持既有库存归属；供应商是进货来源，门店是需求/收货方，三者不得混成同一个对象。

## 2. 功能边界

### 必须完成

1. 生鲜食材、供应商、门店、仓库/储区/储位资料；常温/冷藏/冷冻业务标签。
2. 固定包装整数数量、批次、生产日期、到期日、收货与上架、按批库存与流水。
3. 临期查询、过期与不合格库存阻断、先到期先出（FEFO）。
4. 门店申领、审核、关联出库、完整分配、拣货及发货。
5. 简单配送派单、发车、逐批签收数量、拒收/短缺/破损原因、异常处理记录。
6. 本店数据权限、关键动作幂等与事务一致性、基本业务统计。
7. 只读 AI 库存助手：真实库存/临期/配送查询与解释；无 Key 时业务照常可用。

### 本次不做

散装称重、单位换算、拆包加工、菜谱/BOM、门店消耗与门店库存账、跨仓调拨、多配送中心、采购合同与财务结算、路线优化、地图/GPS、真实冷链设备、司机 App、自动补货、预测模型、AI 自动审批或修改库存。

一期一张申领只对应一张出库单与一张配送单；可含多 SKU、多批次，但只送一个门店。不拆单、不合并多门店配送、不分批发货；库存不足时保持待配货，补货后重试，或在未开始拣货时取消并重提较小数量。签收是一次提交，允许部分接收和异常终结。

温区只是仓储约束与业务标签，不宣称实现全程冷链监控。各食材温度标准不在此方案中编造，若后来增加温度上下限须另行确认来源。现有 IoT 可保留为原系统附加模块，不纳入必过主流程。

## 3. 基础数据与批次

食材：编码、名称、分类、规格描述、计数单位、保质期天数、临期阈值天数、温区、启用状态。示例 SKU：鸡胸肉 1kg/袋、牛奶 1L/盒、土豆 5kg/袋。规格的重量仅用于描述，不参与库存数量换算。

供应商：唯一编码、名称、联系人、联系方式、启用状态。门店：唯一编码、名称、地址、联系人、联系方式、启用状态。禁用后拒绝创建新业务，既有单据仍允许查询和完成履约；被引用的主数据禁止硬删除。

每次收货必须关联供应商、商品、批号、生产日期、到期日。批次身份至少由“货主＋供应商＋SKU＋批号”唯一确定；内部 batchId 在收货后固定并贯穿下游。同批重复收货可累计，但生产日期/到期日冲突必须拒绝。相同外部批号来自不同供应商不得混账。

质量冻结是内部 batchId 级别的逻辑冻结，覆盖该批在所有储位及所有订单中的未发出数量。仅总部/仓管可登记冻结并写原因；冻结后全批禁止新分配、继续拣货和发车，查询立即显示不可配送。已有占用不在冻结动作中自动清除，避免订单仍显示已分配而占用被释放；页面列出受影响的未发货订单，由仓管逐单执行下述终止处理。冻结不等于把所有实物自动搬至隔离位，原储位仍显示实物和冻结标签；不支持通过普通编辑恢复为合格。已发出的历史事实不改写，可登记配送异常。

商品默认保质期用于建议到期日，入库批次明确确认后的日期才是业务依据；修改商品保质期不能改变历史批次。旧数据缺供应商、批次或效期时标为历史待核验，不自动补造真实来源，不纳入新生鲜可配库存。

库存行应能唯一定位“仓库＋货主＋SKU＋批次＋储位”（若原容器字段参与唯一性则一并保留）。上架和拣货只是位置移动，不能合并不同批次，也不能重置原收货时间、生产日期、到期日、供应商。

## 4. 数量与效期口径

### 数量

- 入库计划/实收、申领明细、分配、上架、拣货、发车等业务动作数量均为正整数，范围 `1..2,147,483,647`；后端拒绝 0、负数、小数、空值和超上限值，不静默取整。余额是另一种语义，允许为 0、不得为负；库存流水变更量是有符号值，出库/移出记录可为负数。涉及累计、签收求和或余额计算时使用 `long` 做中间计算，检查范围后再写回 `Integer/INT`，不得溢出。
- 签收按每个发出批次记录接收量 A、拒收量 R、短缺量 M；三者各自允许 `0..F`（F 为该批次正整数发出量），且必须满足 `A+R+M=F`。允许其中任何一项为 0，但三项不可同时为 0；多个批次的合计以 `long` 校验，不能因 `Integer` 溢出而错误通过。
- 库存采用现有整数账，不另建一套生鲜库存余额。存量 `stockQuantity` 为在库，`allocatedQuantity` 为已分配，`availableQuantity` 在本方案中明确为“账面未分配”。P0 核实原字段后，由统一库存服务维护：在库＝账面未分配＋已分配，且各项非负。
- **可配送数量**是账面未分配经过效期、合格状态、来源完整性及可拣货库位过滤后的数量；前端要清楚区分“账面未分配”和“可配送”，不能将旧 available 字段直接称为可配送。
- 暂存待检、隔离、不合格、过期批次即使有账面未分配数量，可配送量也为 0。无需通过过期任务把实体库存删除或归零。
- 仓库总在库包括收货暂存、存储、拣货暂存和隔离位；仓内转移总量不变。全仓可配送量只统计合格的可拣货存储位。
- 入库一次增加实收数量；分配仅从未分配转为已分配；拣货将该批的在库及已分配数量移到拣货位；发车确认一次性减少拣货位在库及已分配数量。派单与签收不得再次扣库存。

### 日期

业务时区 Asia/Shanghai，日期使用日期语义，测试支持固定业务日 T，不依赖真实日期不断变化。为减少边界歧义，一期采用保守业务约定：到期日 D 当天即不可配送。这里是课设约定，不是食品法规判定。

- 生产日期不得晚于收货日；到期日必须晚于生产日期，且收货日当天不得已经到期。
- 剩余天数＝到期日－业务日期。剩余天数 ≤ 0 为过期；0 ＜ 剩余天数 ≤ 食材临期阈值为临期；大于阈值为正常。阈值为非负整数。
- 分配时要求到期日大于“业务当日与计划送达日的较晚日期”；相当于计划送达当天至少剩 1 天。分配按到期日升序，再按原始收货时间、稳定库存 ID 升序。
- 发车再次检查效期和批次质量状态，即使订单前一天已经分配也不能跳过检查。计划送达日期被修改时重新检查全部批次。
- 到货后允许记录过期/破损等拒收异常，不因“已经过期”而阻止门店登记事实；异常不自动回仓增库。

## 5. 业务流程与状态

状态名是逻辑合同；尽量映射原 WMS 枚举，P0 提交映射表，不能为改中文名称重写已有枚举。

### 入库

新建入库 → 审核 → 收货验收 → 上架完成。供应商、批次来源随实收记录保存。收货计入暂存库存，上架仅移动库存；整批验收合格后才能上架到温区匹配的可拣货储位。不合格收货记录可留存，但进入不可配送的隔离位。拒绝超计划收货；分次收货总和不可超计划，同一次操作重试不能重复入账。

上架必须满足食材与储区温区匹配；允许使用统一的收货/隔离暂存区，但这些区域不允许分配。门店不会看见仓内收货任务或改写库存入口。

### 申领与出库

`DRAFT → SUBMITTED → APPROVED / REJECTED`；草稿及驳回单可修改重提。提交后冻结商品与数量，不允许普通编辑绕过审核。计划送达日期不可早于当前业务日。

审核通过在一个事务内建立唯一关联出库单，初始待分配；重复审核不重复建单。所有明细分配成功才进入已分配；任一行不足则整单分配回滚，不保留半张订单占用。审批结果与配货结果分开，库存不足可显示“已审核，待补货”。

`待分配 → 已分配 → 拣货完成 → 已发货`。一期可以沿用原波次/任务，也可以提供“一键为本单生成拣货任务”的简化入口，但仍调用同一库存服务和批次明细，不另写直接扣账捷径。

取消边界：草稿/已提交申领可由本店取消；已审核且尚无拣货执行记录的订单可由仓管取消，在同一事务释放全部占用、关闭出库、取消未发车配送。开始拣货后不支持普通取消，界面及接口明确拒绝；不允许用直接编辑状态修复。

若拣货后发现过期/不合格，必须提供仓管“终止履约并隔离”动作：将本单已拣数量移到不可配送隔离位、释放本单未拣占用、关闭未发车单据并保存原因。隔离实物仍在库，禁止释放成可配送库存；该动作幂等。此处解决因发货阻断造成的死单，不扩展完整逆向物流。

该终止仅针对因效期/质量阻断的未发货订单，不是任意已拣订单的普通取消。一次终止处理整单：已拣各批次全部移到隔离位并解除本单占用；未拣部分在原储位解除本单占用，其中冻结/过期批次仍不可配送，其他合格批次可重新分配。其他订单的占用不被本单动作释放，但同批冻结依然阻止这些订单发货，须逐单处理。全仓实物总量不变，流水保存原/目标储位与批次；不要求本期增加解冻或隔离库存重新上架功能。

### 配送与签收

拣货完成后生成唯一配送单：关联出库单、门店及地址快照、计划送达日、批次明细；填写配送员、联系方式、车牌/车辆备注（后两者可按页面设置必填级别，P1 固定）。一期车牌不建立独立车辆管理系统。

`待派单 → 待发车 → 配送中 → 已签收 / 签收异常 → 异常已处理`。

派单只登记任务，不扣账。“确认发车”作为唯一实际出库动作：出库已发货、配送中、逐批扣库存与流水必须同事务提交；原 WMS 发货入口必须接入同一幂等逻辑，不能出现两个扣库存按钮各扣一次。无需真实快递运单、付费承运商 API 或电子面单。

门店签收按出库批次明细填写：发出 F 为正整数，接收 A、拒收 R、短缺 M 各为非负整数且 **F＝A＋R＋M**。破损可归为拒收原因，不能额外再加一列造成重复扣减。A/R/M 明细一一关联批次；有差额必须选原因并写说明。全量正常接收为已签收，其余为签收异常。

已签收不允许覆盖编辑原数量；异常由仓管补充处理说明、责任分类、处理人、处理时间并关闭，保留原始签收记录。一次性签收重试不会新增第二份收货事实。

本次不建立门店库存账，因此接收数量是门店收货记录；中央仓库在发车时已经扣减。拒收/短缺不自动退回库存。异常处置须明确“门店处置/运输损耗/另行线下处理”等去向；真实退货回仓不在本期功能内，页面明确提示不能凭异常关闭自动恢复库存。

### 追溯与统计

从批次可以查询供应商、收货、库存位置、分配、拣货、出库、配送、签收和异常；从配送单能反查各批次来源。流水必须关联单据/明细、动作、执行人和时间，不能仅依靠备注文本猜关联。

看板只做四类：临期/过期批次数、待处理申领单数、配送中单数、待处理异常单数。库存量按 SKU＋计数单位展示，不把“袋＋盒＋箱”直接相加为总库存件数。统计与列表使用同一过滤及权限范围；显示查询时点，不用随机数或静态假数据。

## 6. AI 约束

先完成 P0～P5 核心业务，再做 P6。最小实现是“后端白名单只读查询＋结构化业务数据＋模型解释”，不做向量知识库建设、不让模型生成任意 SQL、不允许写入工具。

支持三个意图：查询食材可配送库存、查询临期批次、查询配送及异常。回答附查询时间、商品/批次或单号、数字及可核对来源。事实和建议分开；建议不能伪装成已经执行的业务动作。

仓管/总部可访问本权限范围内的库存与配送。门店用户可通过普通业务页面和 API 查询本店申领与配送；AI 仅支持上述三个白名单意图，门店用户在 AI 中只可查询本店配送，不支持通过 AI 查询申领、库存或临期批次。授权过滤在查询层完成，不能把全库数据发送模型后要求模型自行隐藏。

API Key 只在后端环境变量或本地忽略文件中配置，前端、日志和交付文档不得出现。配置模型超时与失败提示；无 Key 或超时显示“AI 当前不可用”和可用的普通业务查询入口，不伪造模型回答。验收的真实调用需要用户可用凭据；没有凭据时 P6 标记待验证，不宣称全部交付通过。
