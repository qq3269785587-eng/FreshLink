# 实施阶段与三天安排

## 1. 推进规则

阶段顺序为 P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7。每阶段只做本阶段，完成后停止并提交证据；用户交 Codex 验收通过后再继续。下表时长是净实现与自测的粗估，不是工期承诺，也不包含等待反馈。

| 日程 | 阶段 | 目标 | 建议时间盒 |
|---|---|---|---|
| 第 1 天 | P0 | 保存现状并走通基线 | 1～2 小时 |
| 第 1 天 | P1 | 生鲜基础资料、门店账号与权限 | 2～3 小时 |
| 第 1 天 | P2 | 收货上架、批次、效期与库存 | 3～4 小时 |
| 第 2 天 | P3 | 门店申领、审批、分配和拣货 | 3～4 小时 |
| 第 2 天 | P4 | 派单、发车、门店签收和异常 | 3～4 小时 |
| 第 3 天 | P5 | 追溯、看板、主题与业务回归 | 1～2 小时 |
| 第 3 天 | P6 | 只读 AI 助手 | 2～3 小时 |
| 第 3 天 | P7 | 干净部署、最终验收与演示交付 | 2～3 小时 |

合计约 17～25 小时净工作量，依赖原框架和页面确实可复用。此估计不来自已完成实施的统计；P0 若发现核心链路缺失，应立即报告具体阻塞与重估，不能静默删掉门店签收、批次追溯或验收。

P0本轮发现：原 `WmsOutOrdersServiceImpl.allocateStock` 直接返回失败，`createWave` 主体停在TODO，因此“原出库主链已可复用”的前提不成立。P3必须补齐真实整单分配，并优先采用本规格允许的一单生成拣货任务路线；原17～25小时不能作为当前保证，P3工作量需重新评估。

优先删减的是：额外图表、导出美化、司机端、独立车辆模块、自动派车、复杂波次界面、RAG/向量库。已在范围内的批次准确性、库存并发、门店隔离、签收异常与 AI 真实查询不因赶工降低标准。AI 凭据可以在 P0 提醒用户准备，P6 前配置，密钥不写入聊天或方案。

## P0：基线、保护与可重复验证

入口：已读完整交接包；只读检查没有被当作完成验收。

- [ ] 保存根前后端工作区的完整源码差异、未跟踪源码和规格快照，记录仓库 HEAD、文件清单及哈希；不覆盖现有修复。备份当前数据库并在独立测试库恢复一次。
- [ ] 固定实际启动路径、JDK/Maven/Node/pnpm/数据库版本及配置入口，区分旧端口进程与新构建，记录现有构建和登录基线。
- [ ] 在专用测试数据上实际走“基础资料→入库→收货→上架→分配→拣货→发货”，记录每步库存与状态；无法运行的步骤给出具体原因及其修复所属阶段。
- [ ] 确定状态映射、整数上限、原库存字段语义、批次唯一键与迁移方式；给出最短的现有波次/打包复用路线，后续不依赖外部快递接口。
- [ ] 建立可执行测试入口、测试库保护、固定日期夹具、证据目录及阶段台账；验证后端测试实际执行，前端构建可运行。

P0 允许补充最小测试配置及一条针对现有规则的有效回归断言，这是建立基线的工作；不要求 P0 提前完成新业务测试套件。后续各阶段按实际业务改动扩展测试。

交付：`baseline.md`、源代码快照/清单、脱敏数据库恢复记录、`state-map.md`、`data-contract.md`、`test-commands.md`、基线问题表。

通过条件：`validation.md` 的 P0 全部满足。允许准确登记原有业务缺口并分配到 P1～P4；环境无法运行、快照缺未跟踪源码、数据库恢复失败、无可执行测试入口则不能通过。

## P1：基础资料与权限骨架

依赖：P0 通过。

- [x] 完成食材规格/单位/温区/临期阈值规则，供应商及门店维护；补齐唯一约束、引用保护和禁用行为。
- [x] 复用框架角色与用户，新增门店绑定；交付总部、仓管、门店 A/B 的角色权限，普通用户不能自改绑定门店。
- [x] 完成迁移、菜单、字典及基础资料演示数据；用一仓、多温区、两门店、多食材验证。
- [x] 完成列表/表单/查询的真实接口联调与输入校验，采用既有组件；接口错误能在页面明确提示。
- [x] 审计原有通用 CRUD、导入导出和系统管理权限，防止门店通过旧入口改库存或访问总部数据。

交付：基础资料页面、增量 SQL、ER/字段映射、账号与权限矩阵（不含密码）、API 清单、P1 证据包。

通过条件：基础资料能保存并刷新读取；无孤立菜单；门店仅能访问已授权功能；无需此时虚构尚未完成的申领/配送页面。

## P2：生鲜入库与批次库存

依赖：P1 通过。

- [ ] 增补供应商和批次事实、生产/到期日期、历史数据待核验标识，打通收货任务与批次引用。
- [ ] 修补收货/上架事务及数量校验，确保暂存到存储不重复增加全仓库存；合格批次才能上架到温区匹配位置。
- [ ] 建立批次级库存与流水查询，明确账面未分配/已分配/可配送口径；实现临期、过期、不合格过滤及仓管按批冻结入口与原因留痕。
- [ ] 检查同批重复收货、同编号不同供应商、不同时点重试、并发收货和同库位多批次，补必要唯一约束与幂等。
- [ ] 用固定 T 的夹具生成可验算库存，提供入库/上架前后数据库快照和接口测试，不依靠手工直接改余额构造“通过”。

交付：收货与库存页面/接口、批次模型迁移、库存口径说明、临期列表、P2 证据包。

通过条件：P2 所有用例通过，收货→上架数量守恒，过期阻断不依赖定时任务，来源和批次可查。

## P3：门店申领与按批配货

依赖：P2 通过。

- [ ] 门店创建/提交/查看本店申领，总部/仓管审核；提交后冻结数据，驳回可改后重提。
- [ ] 审批幂等地产生唯一出库单，保留单据关联和门店地址；库存不足时整单回滚分配，界面支持补货后重试。
- [ ] 按到期日及送达日规则 FEFO 分配，稳定排序、并发防超卖，取消时准确释放占用。
- [ ] 补齐原分配占位实现；采用一张订单生成拣货任务的最短路线，调用同一库存服务，修复拣货目标空批次问题，按批次搬移库存，核验任务数量和出库明细归属。原createWave的复杂策略不作为前置依赖。
- [ ] 实现拣货后质量阻断的“终止履约并隔离”，补齐用户越权、非法状态跳转、重复执行、跨单拣货的负向测试。

交付：申领/配货页面、关联及状态映射、FEFO 与并发测试、全仓/分库位对账、P3 证据包。

通过条件：正常与库存不足流程均可复现；分配不提前扣在库；拣货不丢批；并发无负库存；取消/终止不会遗留占用死单。

## P4：配送、签收与异常闭环

依赖：P3 通过。

- [ ] 生成一出库一配送的内部任务，保存门店地址快照、计划送达日、逐批明细，派单填写配送员等信息。
- [ ] 将确认发车与原发货动作统一；再次检查效期、质量和拣货完整性，同事务扣库存、保存逐批流水、更新出库与配送状态。
- [ ] 门店逐批填写接收/拒收/短缺数量并签收；后端按账号确定门店，验证守恒、状态和幂等。
- [ ] 异常原因、处理意见、处理人/时间及关闭操作可查；拒收和短缺不自动回仓，不覆盖原签收事实。
- [ ] 旧发货/编辑/批量接口回归，验证不能绕过新状态、权限及重复扣账防护。

交付：配送与签收页面、异常列表和处理操作、真实履约证据、P4 证据包。

通过条件：从门店申领到签收全过程能运行，数量和批次准确；原快递服务不可用时内部配送主线仍可完成。

## P5：追溯、看板与主题收口

依赖：P4 通过。

- [ ] 批次详情串联供应商、入库、库存位置、申领/出库、配送、签收与异常；配送详情能反查来源。
- [ ] 四类看板统计与相同条件列表对账，按权限过滤，避免跨 SKU 单位相加；临期排序可定位具体批次。
- [ ] 系统题目、首页、菜单与生鲜演示数据一致；隐藏未纳入角色范围的旧模块，不全局改 Java 包名/数据库名。
- [ ] 在普通桌面浏览器检查空态、错误态、加载态、表格与弹窗，执行 P1～P4 关键回归；修复影响演示的错误。

交付：追溯页、真实统计看板、主题化界面、业务闭环录屏或逐步截图、P5 证据包。

通过条件：可以在无 AI 情况下独立完成课设业务展示；看板和追溯不使用假数据填充。

## P6：只读 AI 库存助手

依赖：P5 通过；真实模型凭据可用。无凭据可完成实现与模拟测试，但不得把真实调用验收勾为通过。

- [ ] 优先复用已安装 AI 能力，提供后端供应商/模型配置和超时；无需额外 RAG、Agent 框架或模型训练。
- [ ] 实现库存、临期、配送三种白名单意图及受权限限制的数据查询，结构化数值由后端提供，模型仅解释。
- [ ] 界面显示查询时间、事实数据、引用单号/批次及回答；无匹配时澄清或明确不支持，不能编造数据。
- [ ] 处理超时、无 Key、限流与失败；恶意文本或用户要求修改库存时无写入能力，凭据不下发前端。
- [ ] 真实模型调用验证三个意图、一次数据变更后的更新答案及门店隔离；保留脱敏请求/响应和数据库对照。

交付：AI 页面/接口、配置示例（占位符）、权限过滤说明、失败处理、真实调用证据、P6 证据包。

通过条件：模型能够基于当前授权数据回答，不能把通用聊天页面或 mock 回答当业务 AI 已完成。

## P7：最终部署、验收与演示

依赖：P0～P6 均通过；未通过项必须明确列出，不能标“全部完成”。

- [ ] 从冻结源码/快照和基线数据库新建可运行测试实例，执行所有迁移与启动步骤，验证环境说明可复现。
- [ ] 对最终源码构建并执行核心自动测试和真实浏览器 E2E，完成 `validation.md` 的最终演示与越权、重复、并发检查。
- [ ] 整理部署说明、角色说明、ER 图、状态图、接口清单、迁移/回退说明、演示脚本与未实现范围，保存脱敏演示数据。
- [ ] 交付源代码版本/完整快照、规格、构建产物和证据索引；关闭临时调试写入口，检查日志及前端无密钥。
- [ ] 提交总验收申请，等待 Codex 判定；若用户要求现场演示，由用户另行确认设备上的实际演示结果。

交付：`outputs/fresh/` 的可运行交付包及清单、P7 证据包、总体验收报告草稿。

通过条件：新环境重建可用、业务全链路通过、必测用例全通过且无阻断缺陷。自动检查、浏览器实测与用户设备/答辩演示分开记录。
