# 生鲜课设改造交接包

题目：**面向连锁餐饮的生鲜食材仓储与配送管理系统**  
方案版本：v1.2（P0 验收后交接补强），2026-11-17。**P0、P1 独立验收通过；P2 尚未开始**。P1 当前结论见 `work/fresh-acceptance/P1/attempt-02/codex-review.md`，原 attempt-01 未通过结论保留。后续两位开发同学按 `outputs/fresh/协作任务书/` 分批交付，负责人验收；GitHub 基线准备完成后再开工。历史 Harness 规则见 [HARNESS.md](HARNESS.md)。

## 已确认的范围

- 一个配送中心、多个连锁门店；门店申领、仓库出库、配送派单、门店签收、异常登记形成闭环。
- 食材按固定规格计数，例如“鸡胸肉 1kg/袋”，数量为整数袋；不支持散装小数称重或拆包换算。
- AI 库存助手保留，在核心业务完成后独立实施。
- 不做地图、路线优化；无额外教师要求，不要求真实温湿度设备。
- 用户要求三天内完成改造。按启动后的第 1～3 天安排，不把工作量估计当作交付保证。
- DeepSeek Harness 分阶段制作；每阶段自测后停下，用户交给 Codex 验收，通过后才继续。

## 核心判断

现有 WMS 适合增量改造，但不能只替换主题文字。现有库存已经有批次、效期，主要缺口是门店身份与数据权限、门店申领到配送的关联，以及贯穿拣货和发货的批次追溯。源码中发现拣货目标库存使用空批次、发货流水未保存批次，必须在业务改造中修正。

P0动态核查补充：订单分配接口对应服务仍直接返回失败常量，波次创建主体仍为TODO，原出库主链尚不可运行。这是P3主要实现工作，优先采取一单生成拣货任务的既定简化路线；不能按“仅修批次丢失即可”估算后续成本。

三天内的主要风险是原有入库和履约链路没有完成完整运行验收。P0 已确认分配/波次缺口，后续按阶段补齐原链；不引入第二套库存账。固定包装、单门店配送单、简单派单和只读 AI 是主动压缩后的范围。

本交接包最初依据迁移前核实的活动源码和本地运行记录编写。本次 P0 已重新构建、隔离恢复数据库并进行实际链路验证；当前验收结论以 codex-review.md 为准，原自测过程见 delivery.md，后续实施规则以当前规格和 CHANGELOG 为准。干净安装和新生鲜完整业务主链尚未验收，不将迁移或原链局部成功写成新业务完成。

## 使用方法

1. 先阅读 P1 attempt-02 独立验收报告及分配给本人的协作任务书；旧 Harness P1 指令仅供历史范围参考，不重复执行。
2. 待负责人提供 GitHub 仓库和已验收基线，再按 P2 起逐批实施。每阶段生成 `阶段交付模板.md` 要求的证据，并报告准确的前后端组合版本或快照。
3. 用户让 Codex“按 validation.md 验收 Pn”，并提供该阶段证据目录。证据不足也不能判为通过。
4. Codex 返回通过、未通过或待验证。只有“通过”且用户让 Harness 继续，才进入下一阶段。

文档位于两个 Git 仓库之外：必须随阶段证据一起归档，不能只提交前端或后端仓库便认为规格也已保存。
