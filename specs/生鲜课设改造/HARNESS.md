当前版本 v2.1，2026-11-18。P0、P1已验收；D1/D2/D3/D4待实施。本次仅改文档，不自动开始业务代码开发。

## 开工顺序

1. 先确认公开仓库最新 main 已包含 v2.1 文档，再从该 main 开始工作；不要用旧标签覆盖新版规格。原机工作根 D:/Yuki/Codex/Project/FreshLink；团队克隆以自身 README 所在目录为根。
2. 读 README、mission、state-contract、roadmap、validation，再读本人任务书。写库前按对应环境入口核验实际连接和运行版本。
3. A负责后端、SQL和业务测试，B负责前端、联调与演示材料。A先给最小接口合同，明确字段、状态、数量和错误响应，双方可并行；共享文件指定一人维护。
4. D1完成后再推进D2；D2入库效期完成必要检查后联调D3；D3出库配送联通后进入D4。每天集中集成，阻断即时沟通，不把每个小改都做成全阶段验收。
5. 小批次保存可追溯Git版本/差异，运行影响面测试，PR附精简证据。D4在最终前后端组合版本集中构建和完整演示，由负责人验收。开发者不代填验收通过。

原机使用 test-environment.md 的隔离库，团队副本使用 scripts/team/ 和本机配置。不要误将普通3100/8080原业务库用于写入验收。测试记录写 work/fresh-acceptance/Dn/attempt-XX/ 或团队明确的新work证据目录，不覆盖历史。凭据只在本机配置，下载缓存放项目内。

首次迁移要验证可安全重跑；普通开发无需反复恢复数据库、归档全部源码或逐层解包构建物。版本绑定采用Git提交及未提交差异/必要文件哈希。最终代码改动后必须重跑受影响检查，不能复用旧结果冒充新版本。

遇到原出库占位实现，不继续补复杂波次；沿最小人工选批路径接入原库存账。库存事务、防重扣、权限与批次准确性必须保住。若超时，优先删视觉美化和非必要展示，不悄悄用假数据或跳过库存校验。
